================================================================================
MANIFEST: tests/assets/authoring
The sample-video corpus, file by file - what it is and how it was verified
================================================================================

Written by tools/CodeBrix.VideoPlayback.AssetAuthoring on 2026-08-29 17:11:09 (local time).
Regenerate it, and everything it describes, with:

    dotnet run --project tools/CodeBrix.VideoPlayback.AssetAuthoring -c Release

Every command line below was BUILT by CodeBrix.VideoPlayback.Authoring and RUN by
CodeBrix.VideoProcessing, which launches the host's ffmpeg as a child process. The
generator never invokes ffmpeg itself, and the CodeBrix-Mode2 files are muxed by the
playback library's own bespoke muxer rather than by ffmpeg at all.

WHAT THIS RUN RE-ENCODED: CodeBrix-Mode2.
Everything else below was read back and re-verified, not re-encoded; its command line
is re-derived from the plan, which is where it came from in the first place, and its
encode time is the one the previous manifest recorded.

REPRODUCIBILITY. The SHAPE of this corpus is deterministic - the same twenty-four files,
the same resolutions, the same settings, the same command lines every run. The BYTES
are NOT: the Matroska muxer writes a random track UID and a fresh muxing date into
every file, so two runs of this tool produce files that differ even when the encoder
has made an identical bitstream. Those fields are fixed-length, so the sizes below do
tend to come back the same - but do not pin these files with a hash, and do not treat
a size that moves by a few bytes as a fault. The CodeBrix-Mode2 files carry no random
field at all, but the AV1 encoder is itself only deterministic for a fixed build and
thread count, so the same caution applies to them.

================================================================================
ENCODER SETTINGS, BY RESOLUTION RUNG
================================================================================

  rung   landscape     portrait      preset  crf  keyframes  audio
  -----  ------------  ------------  ------  ---  ---------  ---------
  4k     3840x2160     2160x3840     6       28   60 frames  128 kbit/s
  hd     1920x1080     1080x1920     5       26   60 frames  128 kbit/s
  720p   1280x720      720x1280      4       24   60 frames  96 kbit/s

  Video   libsvtav1, 8-bit yuv420p, 30 frames per second, scaled with lanczos.
  Audio   libopus for MKV, WebM and CodeBrix-Mode1; libvorbis for CodeBrix-Mode2.
          2 channels at 48000 Hz throughout, at the bit rates in the table above.
          The rungs are the SAME numbers for both codecs, so the two ladders stay
          comparable. Mode2 is Vorbis rather than Opus because Mode2 is the flavour an
          application ships inside itself, and a Vorbis file plays with the core
          playback package alone - an Opus one needs the application to add
          CodeBrix.Audio.Opus and call its Register().
  Keyframes every 60 frames is two seconds at 30 frames per second - set
  explicitly, because the encoder's own default interval is far longer and a long
  interval is exactly what makes a scrub feel slow.

  The preset gets FASTER as the frame gets bigger and the rate factor gets LOWER as it
  gets smaller: encode cost scales with the pixel count, and AV1's rate factor is
  resolution-relative, so this keeps both the wall clock and the perceived quality
  roughly level across the three rungs.
